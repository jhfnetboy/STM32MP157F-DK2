## 概述

本文档设计适用于清迈社区实验的去中心化密钥管理系统 (KMS) 架构,目标是 3-5 节点,实现技术验证、社区运营和经济模型测试。

## 架构目标

### 核心目标

1. **去中心化**: 无单点故障,节点平等
2. **安全性**: 基于 TEE 的密钥隔离和保护
3. **可用性**: 任意节点故障不影响服务
4. **社区化**: 节点由社区成员运营,共同治理
5. **经济激励**: 通过代币激励节点运营者

### 技术指标

| 指标 | 目标值 |
|------|--------|
| 节点数量 | 3-5 个 |
| 容错能力 | 最多 1-2 个节点故障 |
| 响应时间 | < 100ms (本地网络) |
| 吞吐量 | > 100 TPS (签名操作) |
| 可用性 | > 99.9% |

## 密钥管理策略

### 分布式密钥生成

#### 方案 A: 独立密钥 + 备份分片 (推荐 Phase 3)

**原理**:
- 每个节点独立生成完整密钥
- 使用 Shamir Secret Sharing 将密钥分片
- 分片分发到其他节点备份

```
节点 1: 生成 Key1 -> 分片为 [K1_S1, K1_S2, K1_S3]
        保留 K1_S1,发送 K1_S2 到节点2,K1_S3 到节点3

节点 2: 生成 Key2 -> 分片为 [K2_S1, K2_S2, K2_S3]
        保留 K2_S2,发送 K2_S1 到节点1,K2_S3 到节点3

节点 3: 生成 Key3 -> 分片为 [K3_S1, K3_S2, K3_S3]
        保留 K3_S3,发送 K3_S1 到节点1,K3_S2 到节点2

恢复: 任意节点故障,可从其他节点恢复 (需 threshold 个分片)
```

**优点**:
- 实现简单
- 密钥恢复快速
- 适合 Phase 3 验证

**缺点**:
- 密钥实际上仍在单节点生成
- 需信任生成节点

#### 方案 B: 阈值签名 (TSS) (长期方案)

**原理**:
- 密钥从不完整生成
- 使用 MPC 协议 (如 GG20) 生成密钥分片
- 签名时无需重构私钥

```
初始化: 3-of-5 阈值
  节点1: 生成分片 S1
  节点2: 生成分片 S2
  节点3: 生成分片 S3
  节点4: 生成分片 S4
  节点5: 生成分片 S5

签名: 任意3个节点协同签名,无需重构私钥
  节点1 + 节点2 + 节点3 -> 生成有效签名
```

**优点**:
- 最高安全性
- 密钥永不重构
- 更符合去中心化理念

**缺点**:
- 实现复杂
- 需要 MPC 库 (如 tss-lib, multi-party-ecdsa)
- 延迟较高

**推荐库**:
- [tss-lib](https://github.com/bnb-chain/tss-lib)
- [multi-party-ecdsa](https://github.com/ZenGo-X/multi-party-ecdsa)

### Phase 3 推荐方案

**第一阶段 (3个月)**: 方案 A (独立密钥 + 分片备份)
- 快速验证可行性
- 建立社区信任

**第二阶段 (6个月)**: 升级到方案 B (TSS)
- 提升安全性
- 支持更复杂的治理模型

## 数据同步和一致性

### 元数据复制

需要同步的数据:
1. 密钥元数据 (Key ID, 创建时间, 权限)
2. 访问策略
3. 审计日志
4. 用户/应用配置

### 同步方案

#### 方案 A: 主从复制 + 自动故障转移

```
Primary Node (动态选举)
  ├── 处理写操作
  ├── 同步到 Secondary Nodes
  └── 心跳检测

Secondary Nodes (只读)
  ├── 处理读操作
  ├── 接收复制数据
  └── 主节点故障时选举新主节点
```

**实现**:
- 使用 etcd / Consul 进行领导选举
- PostgreSQL 主从复制存储元数据

#### 方案 B: 多主复制 (CRDT)

```
所有节点都可写入
  ├── 使用 CRDT 解决冲突
  ├── 最终一致性
  └── 无需领导选举
```

**实现**:
- 使用 CRDTs (Conflict-free Replicated Data Types)
- 库: automerge, yjs

### Phase 3 推荐

**元数据**: 方案 A (etcd + PostgreSQL 主从)
- 简单可靠
- 成熟的故障转移

**审计日志**: 方案 B (仅追加,无冲突)
- 每个节点独立记录
- 定期归档到中心存储

## API 设计

### AWS KMS 兼容 API

```
POST /api/v1/keys
  - 创建密钥 (分配到具体节点)

POST /api/v1/keys/{key-id}/sign
  - 签名操作 (路由到持有密钥的节点)

POST /api/v1/keys/{key-id}/encrypt
  - 加密操作

GET /api/v1/keys
  - 列出密钥 (聚合所有节点)

DELETE /api/v1/keys/{key-id}
  - 删除密钥 (同步到所有节点)
```

### 健康检查和监控

```
GET /health
  - 节点健康状态

GET /metrics
  - Prometheus 格式指标

GET /status
  - 节点同步状态,连接状态
```

## 社区治理

### 节点准入

1. **技术审核**: 验证硬件,网络,OP-TEE 配置
2. **社区投票**: 现有节点投票是否接纳新节点
3. **保证金**: 质押一定数量的治理代币
4. **SLA 承诺**: 承诺 95%+ 在线率

### 治理决策

通过链上投票:
1. **参数调整**: 手续费,超时时间等
2. **节点移除**: 移除不合规节点
3. **协议升级**: 升级 KMS 协议版本
4. **资金使用**: 社区资金分配

### 激励机制

#### 收入来源

1. **服务费**: 每次签名/加密操作收取小额费用
2. **订阅费**: 企业用户包月/包年
3. **捐赠**: 社区捐赠和资助

#### 分配方案

```
总收入 = 100%
  ├── 节点运营激励: 70%
  │   ├── 按在线时间分配: 40%
  │   ├── 按处理请求数分配: 20%
  │   └── 按质押代币分配: 10%
  ├── 社区开发基金: 20%
  └── 保险基金 (故障补偿): 10%
```

## 安全设计

### 威胁模型

| 威胁 | 缓解措施 |
|------|---------|
| 单节点被攻破 | TEE 隔离,密钥分片 |
| 网络中间人攻击 | mTLS, VPN |
| DDoS 攻击 | 速率限制,负载均衡 |
| 社会工程 | 多签授权,审计日志 |
| 节点运营者恶意 | 阈值签名,社区监督 |

### 审计和监控

1. **操作审计**: 所有密钥操作记录链上
2. **节点监控**: Prometheus + Grafana
3. **异常告警**: 异常流量,节点离线
4. **定期审计**: 社区定期审计节点

## 灾难恢复

### 备份策略

1. **密钥备份**: Shamir 分片分布在所有节点
2. **配置备份**: Git 仓库存储配置
3. **数据备份**: 每日备份到 IPFS/Arweave

### 恢复流程

**场景 1: 单节点故障**
- 自动故障转移到其他节点
- 从分片恢复密钥

**场景 2: 多节点故障 (灾难)**
- 使用离线冷备份恢复
- 社区治理决定恢复策略

## 性能优化

### 缓存策略

```
Redis 缓存层
  ├── 密钥元数据缓存 (TTL: 5min)
  ├── 访问策略缓存
```

```
Nginx / HAProxy

  └── Session Sticky (可选)
```
